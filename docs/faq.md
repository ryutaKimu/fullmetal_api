# API仕様
## Q1 1回のリクエストで1言語だけ返すのはなぜ？
A. レスポンスをシンプルにするため。利用側はこうすることで扱いやすくなる。内部データは言語別に保持。レスポンスは指定された言語の値を返す。

## Q2 レスポンスを data で包んでいるのはなぜ？
データの有無に関わらず、レスポンスの値を揃えるため。利用側はdataをみて、nullかどうかを確認するだけで済む。将来、総件数などの情報を追加する場合も、data の横に項目を足すだけで対応できる。

## Q3 該当データがないとき、404や204ではなく 200 + { "data": null } を返すのはなぜ？
MVP版では外国語版を採用していないため、後続での対応になる。開発側で想定していることなので、異常値ではない。
204はボディが空になり、利用側でJSONとして扱いにくいため採用していない。

## Q4 400エラーの error を data の中ではなく、同じ階層に置いたのはなぜ？
data の中に入れると、エラー時も data がnullでなくなり、利用側が「データがある」と誤判定するため。 data の中身は常にナレーションのデータだけ、という一貫性を保つ

# データ
## Q1 未翻訳の言語を、空文字やキーなしではなく null にしたのはなぜ？
空文字だと、「本当に空」なのか「未翻訳」なのか区別できない。
キーなしだと、読み込む側でキーの有無を確認する必要がある。
また、JSONファイルを見たときに、"en": null で未翻訳であることがひと目でわかる。

## Q2 titleだけ英訳済みで、narrationsが未翻訳という状態を許可しているのはなぜ？
取得時に「titleとnarrationsの両方が非nullのもの」だけを対象にするため、中途半端なデータがAPIから返ることはないから。 これにより、英訳を段階的に進められる

## Q3 空文字や空配列を禁止しているのはなぜ？
「未翻訳」を表す書き方を null の1つに統一するため。 空文字や空配列を許すと、未翻訳の表現が複数できてしまう。

## Q4. narrations を文字列配列にしたのはなぜ？
本APIの使用例としてbotが想定され、分割して配列で保持していた方が、使いやすいため。

## Q5 id を持たないのはなぜ？
1話につきナレーションは1件のみなので、episode で一意に特定できるため。

# 実装方針
## Q1 JSONを起動時に1回だけ読み込むのはなぜ？
総データは64と固定のため、DBを用意する必要がなかったから。

## Q2 go:embed でJSONを埋め込むのはなぜ？
デプロイ時にJSONファイルを別で配置する必要がなくなり、「ファイルが見つからず起動できない」というトラブルを防げるため。データ更新時は再ビルドが必要だが、どのみち再起動が必要なので手間は変わらない。

## Q3 レイヤー構成を handler / service / repository にしたのはなぜ？
拡張を見越して、MVPの段階から責務を分けておくため。後から切り分けるのは手間がかかる。
- フラット構成：手軽だが、後で分けるのが面倒
- クリーンアーキテクチャ：この規模ではファイルや定義が増えすぎる
- 機能単位：機能が1つのため、3層と大きな差がない

## Q4 repository を interface で定義するのはなぜ？
将来JSONからデータベースに変える場合も、serviceを変更せずに差し替えられるため。 テスト時にダミーデータを使うのも簡単になる
