# レビュー観点について
セルフレビューにあたり、必要な観点から品質を確認する。
大きく分けて、二つの観点から確認すること

# 業務観点
- 設計書通り動くか
- 設計書の考慮漏れはないか
- errorやwarningが出ていないか

## 設計書通り動くか
機能要件と照らし合わせ、プロダクトコード/テストコードを実行する。
異常系についての確認も行い、デグレについても確認すること

## 設計書の考慮漏れはないか
実装段階で考慮していなかったエラーへの対応や制約を見つける。
設計書への反映とコードを修正する。

## errorやwarningが出ていないか
1. errorやwarningの原因を特定する。
2. 修正方法を決める。
3. 着手。
4. 解消したかどうかを確認する。


# 非業務観点
- 命名規則に忠実であるか
- 変数・関数のスコープは最小限にする
- 長すぎるロジックは分割する
- 共通のロジックは共通のロジックとして切り出す
- 言語を理解して実装する
- ディレクトリ構成に従ったところにロジックを書く
- コメントを入れる

## 命名規則に忠実であるか
言語ごとに規則があるので、そちらを確認すること。

## 変数・関数のスコープは最小限にする
一つのメソッドでしか使わないのにグローバルに変数を置いたり、
一つの関数で複数の処理を行わない（単体テストがしづらくなる）

## 共通のロジックは共通のロジックとして切り出す
複数箇所で使用されている同一のコードは共通化すること
共通化後、再テストを実施すること

## 言語を理解して実装する
言語仕様を確認し、目的に対して可能な限り適切な手段を採用すること
無闇に独自メソッドを用意しない。（テストケースが増える）

## ディレクトリ構成に従ったところにロジックを書く
レイヤーに分けている場合、追加ロジックが適切なレイヤーに置かれているかを確認する
DB処理をサービスにはおかないなど。

## コメントを入れる
コードからは読み取れない仕様を反映させているロジックについてのみコメントをすること
コードを読めばわかる内容については記載しない。
